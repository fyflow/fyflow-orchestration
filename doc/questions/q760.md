# Q760 — the input a task's worker sees after its transform

[ADR 0128](../decisions/0128-what-a-node-was-handed-is-read-by-replaying-the-run-to-its-composition.md) rule 4 answers a
task with the envelope `dispatch` built — `{ settings, input, transform? }`, `FD-C5`, `FD-C6` — which is what the driver
handed `createTask` and what the worker wrapper receives. **Where the node declares a `transform`, the worker's own code
sees something else**: the wrapper evaluates `transform.expr` in `transform.lang` over `input` first
([ADR 0051](../decisions/0051-a-transform-is-a-declared-expression-in-a-registered-language-applied-in-the-types-worker-wrapper.md)).
The envelope carries everything that determines it — the input and the expression — so a person with the language can
derive it; a reading cannot, without running that language.

**What building it would cost**: an ASYNCHRONOUS reading (a language's evaluator is async — P17 fact 1), the language's
worker half loaded in the reader (a `data:` or file URL the registry names, `RT-R10`'s concern where the reader is a
browser), and an answer that is the language's, not the driver's — so P42 (a1)'s *it IS the driver's composition*
would not hold of it. `tryTransform` (`AGENTS.md` section 15) already evaluates a transform over a sample a person gives,
which is one road a consumer can take today: hand it the envelope's `input`.
