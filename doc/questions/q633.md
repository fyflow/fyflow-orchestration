**Raised by [W167](../work-items/w167-the-exit-artifact-a-runtime-that-is-its-registry-on-real-workers.md)**, P37's exit
artifact, by the maintainer's answer of 2026-10-16. **It is a defect**: a correct payload is refused and a wrong one is
admitted, on the road a flow published to a running runtime takes the moment its FIRST node transforms.

**Measured** (`C:/tmp-w167/fdr4-entry-transform.ts`, scratch, not in the tree; node 24.20.0, on W167's final tree): a worker
whose `inputSchema` requires `label` (a string), and an ENTRY node of its type declaring the JSONata transform
`{ "label": word }`.

| payload | what the transform makes of it | `start()` | `tryTransform(…, { input: payload })` on the same node (W166) |
|---|---|---|---|
| `{ word: "x" }` | `{ label: "x" }` — what the worker requires | **REFUSED** — `BoundaryRefused`, *$.label required* | `transform-passes` |
| `{ label: "y" }` | `{}` — `word` is absent, so JSONata drops the key | **ADMITTED** — the run completes, and the worker RECEIVED `{}`, which its own `inputSchema` refuses | `transform-fails`, *$.label required* |

**Same node, same value, opposite verdicts** (the sharper form is W167's conformity reader's; its probes were scratch
files of that reader's session, `w167-fdr4.ts` and `w167-fdr4-given.ts`).

**The cause.** The start boundary (`src/driver/driver.ts:1527-1549`) walks `boundaryTargets`, composes each target's value
through its `needs` (`compose`) and holds THAT to the worker's `inputSchema` (`findings`); the node's `transform` is never
applied. **What the spec says.** `FD-R4`'s row DOES decide which value is held — *each value composed through the node's
`needs` as `enter` composes it* — and is SILENT on a transform. By implication it is inconsistent with the rest of the
spec, which treats `inputSchema` as what the worker receives AFTER the transform: the `transform` subsection and `FD-C5`
(*`input` is THE VALUE THIS NODE RECEIVES*), the wiring table's `transform-passes` (the transform's RESULT held to the
consumer's `inputSchema`), and v0.38's `given` row (W166 — the result of the given input held to the `inputSchema`).

**The design constraint.** `start()` is SYNCHRONOUS (`src/driver/driver.ts:1499`) and a transform's evaluation is
asynchronous — it runs in the language's worker half, by `import()` — so applying the transform at the boundary is not a
one-line fix. The roads:

| | road | what it costs |
|---|---|---|
| **(1)** | `start()` evaluates the transform before holding the boundary — an ASYNC start | BREAKING: `Driver.start` and `Runtime.start` return promises, and `FD-R4`'s *thrown at the caller before the driver counts itself started* becomes a rejection |
| **(2)** | a TRANSFORMING entry's payload is not held at `start` — UNCHECKED, as a worker declaring no `inputSchema` already is | no breaking change; the transform's own failure at `run()` (a `TransformFailed` task failure, P17 decision 5) and the worker's result are the only checks left on that road |
| **(3)** | a SEPARATE schema for what the transform receives — the node's, or the type's | a new declaration and a new spec keyword; the boundary holds the payload to it and nothing else |

**What we do meanwhile.** Nothing is wrong for a flow whose entry declares no transform — W167's exit block is one (B's
entry `prep` transforms nothing). A consumer whose first node transforms can pass `validateBoundaries: false`
(`RuntimeOptions`), which turns `FD-R4` off runtime-wide, both boundaries; or put an untransformed node first.

**2026-10-16, ROUTED at [P37](../plans/p37-a-runtime-is-its-registry.md)'s retro (g)** — the maintainer: owned by
[P34](../plans/p34-what-cancelling-stopping-and-pausing-a-run-do.md), and it lands before orchestration 0.8.0 is published.
P34's declaration measures it and puts the road — (1), (2) or (3) above — as its own stop-and-ask.
