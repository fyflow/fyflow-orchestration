## The case

A node reads a **file stream or a network stream** and the stream yields items over time. Each item should start
its processing in the flow **as soon as it is read**. Waiting for the stream to end before the first item is
processed is the wrong shape for such sources: the first result is late by the whole stream, the whole stream is
held in memory as one array, and a stream that never ends (a feed, a socket) never starts anything at all.

**Whether such a source must also work INSIDE a `map` is not known yet** (the maintainer, 2026-10-25). The
case is a source at any position in a flow; nesting is a later question.

## What exists at 0.12.0

| channel | what it does today | why it does not serve the case as it stands |
|---|---|---|
| `map` | fans out over `over`'s array, read from a SETTLED task's result | nothing starts before the source settles, the whole stream is one array, an endless stream never settles |
| `context.emit(name, data)` - `task.message` | passed through to the caller as `onTaskMessage` (`spec/run-state.md` `RN-R42`, [ADR 0114](../decisions/0114-a-tasks-attribution-is-fields-and-its-messages-and-progress-are-passed-through.md)) | produces no record (`spec/outcome-record.md` `OR-R4`), so it routes nothing; and the scheduler's transport is LOSSY - over the pool's `messages.maxBuffered` (100 per 20 ms by default) emits are discarded and only counted in `dropped`, and a crashed worker loses what it had not sent (`node_modules/fyflow-scheduler/AGENTS.md` section 6) |
| `context.spawnTask(...)` | the scheduler adds the task itself; the driver reports its settlement and otherwise ignores it ([ADR 0023](../decisions/0023-an-inbound-settlement-is-this-runs-only-if-this-driver-dispatched-it.md)) | [ADR 0001](../decisions/0001-routing-executes-in-the-driver-outside-the-scheduler.md) refuses it for flow control: spawn is lineage and cannot join, and it moves the flow into worker code where it cannot be validated, rendered or versioned. The worker picks the id (Q13's silent overwrite) and the worker type; nothing logs, resumes, joins or cancels it |
| **one run per item, started by the Host** | the Host reads the stream and starts a run per item - the library's own shape, *instantiated per workload at thousands at a time* (`doc/concept.md`) | works today with no change. **What it lacks**: nothing gathers the items' results, there is no run for the stream itself to observe, stop or resume, and the reading happens in the Host rather than in a worker on a scheduler |

## The shapes, sketched and not decided

| | shape | fits when |
|---|---|---|
| **A** | **Host-level**: one run per item, as above, possibly with a library helper that reads an async iterable and starts runs under a bound | each item is independent and nothing is gathered at the end |
| **B** | **A streaming source node in the flow**: a task whose worker `emit`s items; each item opens one branch of a region the source opens, like a map's instance, keyed by its sequence number; the source counts as a live branch until it settles, so the region's join cannot fire while items may still come | the stream belongs to one run, its items' results are gathered (or counted) at a join, and the run is observed, stopped and resumed as one |
| **B without a join** | as B, but the region has no join: each item's path ends at an `end` node, and the run ends when the source and every item have | items are processed and delivered, not gathered; an endless source is a run that does not end until stopped |

For B, each item would become a LOGGED element, so run state stays a fold of the log
([ADR 0014](../decisions/0014-the-driver-produces-the-folds-ordered-input-sequence.md)); the count would be checked
against the attempt's `seq` when the source settles; a `dropped` count or a `seq` gap would fail the source BY
NAME, never a silently short region; a join would key by sequence number (`spec/join-policy.md` `JP-R12`'s own
key).

## What a plan would have to answer

| # | question |
|---|---|
| 1 | **A or B** - is the stream one run or many; are items gathered at the end. fyflow-app's case decides it |
| 2 | **Loss** (B): an upstream `messages` mode that blocks or fails rather than drops (an S item in [scheduler-upstream.md](../scheduler-upstream.md)), or a refusal on a gap with the default transport |
| 3 | **Retry** (B): a retry restarts `seq` at 0 and re-reads the stream; the driver must not dispatch an item twice, and the re-read must yield the same items or be refused `diverged` per item |
| 4 | **Resume** (B): logged items stand and the source re-runs - from the start (deterministic re-read, already-logged items skipped) or from a CURSOR the source logged with each item. A network stream cannot be re-read, so a cursor or a refusal by name |
| 5 | **Source failure mid-stream**: what the items already started, the join and the run outcome become |
| 6 | **Backpressure**: a bound on items in flight, and what the source does when it is reached - a worker cannot be paused through `emit`, so either items queue in the driver (memory) or the source is told to wait (a channel the scheduler does not have) |
| 7 | **An endless source**: retention - every item is a log element, so a run that never ends grows without bound (`spec/run-state.md` `RN-R13`'s concern, [Q19](q19.md)) |
| 8 | **Inside a `map`** - not required yet; a source per map instance would be B nested, and region identity ([ADR 0062](../decisions/0062-a-region-instance-is-its-opener-and-the-openers-own-branch-path.md)) already covers an opener entered many times |
| 9 | **Spawn as the channel instead of emit**: adopting `task.spawn_request` would supersede ADR 0001, and the scheduler adds a spawned task itself, so the driver could not mint its id. Emit keeps the definition as the only place that says what runs on an item - the maintainer's leaning on 2026-10-25 was emit, which is a leaning and not a decision |
