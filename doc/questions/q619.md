**Raised by [W163](../work-items/w163-what-start-refuses-that-the-flow-does-not-decide.md)** (its conformity reader's
observation 8). `FD-R6` ([ADR 0097](../decisions/0097-what-start-refuses-that-the-flow-does-not-decide.md) rule 1)
reads a node's `workerGroups` and its pool's `groups` — the two sets the scheduler resolves a KEY for
(`_groupsForTask`, `_resolveResourceKeys`, at the pin) — and NOT a pool's `residentGroups`, for which the scheduler
resolves no key and therefore does not throw.

**Measured by W163's author, 2026-10-15**, node 24.20.0 and deno 2.9.6, each with the type's pool inline and threaded:
a registry declaring `api` of type `KeyedRateLimitGroup` (`windows: [{ limit: 5, windowMs: 1000 }]`) and a type whose
pool declares `residentGroups: ['api']`, `idleTimeout: 1000`, `maxThreads: 2`, and no `groups`; a two-task flow on that
type, no `createTask`. In all four: `runtime.check(flow)` returned `[]`; `start` did not throw; `done` settled
`completed`; and the group's keys afterwards were **`[""]`** — one bucket with the EMPTY key — with
`stats.totalAcquired` 1 and `totalReleased` 0 (the worker holds it until it idles out). **So every worker of every pool
holding the group resident is counted in one shared bucket, silently** — the very outcome the scheduler's own comment on
its throw names (*"A keyless task would otherwise silently share a bucket with every other keyless task"*), reached by
the one road where it does not throw.

**The options.**

| | option | what it changes |
|---|---|---|
| A | **widen `FD-R6`**: a task node whose pool holds a built-in keyed group as RESIDENT is refused too | one rule, one refusal class — but a `createTask` cannot help (a resident group is acquired per WORKER, and no task's `limitKey` is read for it), so `LimitKeyMissing`'s two roads would be one |
| B | **a registry refusal at `createRuntime`**: a built-in `KeyedRateLimitGroup` named in any pool's `residentGroups` is refused by the resolver, naming the pool and the group | the defect is the REGISTRY's — no flow and no `createTask` changes it — so refusing it where the registry is read is the precise place; a document that does this today stops building |
| C | **accept it as stated**: a keyed group held resident is one bucket by construction, and say so in the spec's group-types table and `AGENTS.md` | nothing refused; a consumer reading the docs knows; the silent sharing remains for one who does not |
| D | **hand on** to whoever builds [Q248](q248.md)'s key derivation — a document `keyFrom` would key a resident acquire as it keys a task's | defers it; until then A, B or C's question stays open |

**2026-10-16, ROUTED at [P37](../plans/p37-a-runtime-is-its-registry.md)'s retro (i): option B** — the maintainer. A
built-in `KeyedRateLimitGroup` named in any pool's `residentGroups` is refused by the resolver at `createRuntime`, naming
the pool and the group; built as one row of [P34](../plans/p34-what-cancelling-stopping-and-pausing-a-run-do.md)'s
declaration, so it ships in 0.8.0. Open until that row lands.
