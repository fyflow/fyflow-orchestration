**Raised by [W197](../work-items/w197-the-cost-check-and-the-exit-artifact.md)**, P39's last item, while sizing the cost
suite's `needs` arm — **found by its WALL, which no count of P39's sees.**

**Measured** (the session scratchpad's `w197/drv-time2.ts` and `drv-time3.ts`, outside the tree): an `ingest` task, then a
`map` whose branch is `work` followed by `post` — with `post` declaring `needs: { w: 'work', it: '.' }`, a reference to its
OWN instance's `work`; beside it `test/fold/map-cost.test.ts`'s own flow, whose `post` reads one small output. `task.running` (attemptNumber 1) before every
settlement, the queue walked by index.

| items | driver, `post` reads `work` (`drv-time2.ts`) | the suite's own flow, `post` reading a SMALL `ingest` with the items in a `list` task before the map (`drv-time3.ts`) |
|---|---|---|
| 2,000 | 673 ms (4,001 settlements) | 68 ms (4,002) |
| 8,000 | 20,492 ms (16,001) | 215 ms (16,002) |
| 16,000 | 96,919 ms (32,001) | 394 ms (32,002) |

**30x for 4x the items, then 4.7x for 2x**: quadratic. A CPU profile at 6,000 items: **`outputIsVisible` 36.8% self,
`resolveReference`'s filter callback 23.0%, `resolveReference` 11.4%, `regionChainOf` 10.8%** — the visibility predicate,
called once per output of the named node, on every read.

**The cause.** `resolveReference` (`src/driver/driver.ts`, `const visible = (produced.get(t.node) ?? []).filter((e) =>
outputIsVisible(…))`) takes EVERY output the named node has produced — one per map instance that settled it — and asks
[ADR 0044](../decisions/0044-a-reference-is-visible-when-two-paths-agree-on-the-regions-that-contain-both-of-them.md)'s
predicate of each, then sorts what survives. For a reader inside the same instance exactly one survives, and finding it
costs the node's whole list. [W195](../work-items/w195-the-drivers-per-task-view-of-its-log.md) made `outputs()` — the
by-node index this reads — grow incrementally (ADR 0121), so the INDEX no longer costs the run per read; the SEARCH of
one node's list still does. **P39's counts cannot see it**: `taskLog.visits` counts the log records handed to
`effectiveOutcome`, and this reads none.

**Not [Q186](q186.md).** Q186 is a reference to a LARGE VALUE inside a map — the clone per read, `structuredClone` 89% of
the profile when `post` read an `ingest` whose result held the item list (10.8 s at 8,000 items). This is a reference to
a SMALL value: the cost is the search, and it grows with the item count whatever the value's size.

**What a consumer does meanwhile.** Nothing breaks; a map whose branch tasks read no other node of their branch — the
app's repro, every row of P39's measurements — is linear. A branch that needs what an earlier task of its own branch
returned can take it as `"."` (what the task would have received anyway) where the earlier task is its only predecessor,
which composes without the search. The roads for a fix, each a design question this file does not answer: an index of a
node's outputs by branch path beside `outputs()`'s list, consulted where the reader's region chain contains the output's
whole map instance; or `outputIsVisible` asked only of the entries a region-chain prefix selects.

**RESOLVED 2026-10-22 by [W199](../work-items/w199-the-reference-index-a-read-costs-its-answer.md) under
[P40](../plans/p40-what-a-reference-read-costs-inside-a-map.md), [ADR 0124](../decisions/0124-a-reference-read-costs-its-answer.md)**
— the closing condition's first road, for every case of the visibility rule (P40 (b)), not only the reader's own
instance. The driver files a node's outputs under `visibilityKey` — the first `d` segments of their branch paths, `d` the
depth the reader and the target share; `outputIsVisible` is restated through the same function — and a read takes its
group. `outputsCache.examined`, a private count of the entries the index touches, is pinned EXACTLY in
`test/fold/map-cost.test.ts` at 2,000 / 8,000 items: `2n` one step back (this question's flow), `2n` two steps back, `7n`
in a nested map, `4n` from a sibling map of three slots — 4x, bound 6x — with the filter, the per-read sort and the
per-output depth each restored and red. Re-taken on W199's tree, the driver alone, node 24.20.0 / deno 2.9.6: **68 / 223 /
442 ms and 79 / 258 / 560 ms** at 2,000 / 8,000 / 16,000 items, against **701 / 22,033 / 99,029 and 474 / 12,006 /
64,208** on `6006caa`. The profile at 8,000 items is flat — `structuredClone` of each result leads it. [Q186](q186.md)'s
cost, the clone of a large value per read, is unchanged and still deferred.
