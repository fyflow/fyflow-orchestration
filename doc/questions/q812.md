**What failed.** All five assertions of the one run, each consistent with the task not having settled when the row
read it: the fold's outcome `running` for `awaiting_action`; no outcome record for `merge` where one `user_action`
record with no result was expected; `snapshot()` holding `merge`'s id where the record-kind subsequence was empty; and
the live task carrying the error string (*could not be cloned*) the record did not yet have.

**Why it is a question and not a fix.** Nothing was changed to make it pass: it passed on the next four runs. A row
that reads a threaded run on a timing it does not control would fail rarely and under load - this gate ran three
runtimes' suites before L6 - and `examples/l6.ts` is the only rung that touches real workers, so a rare red there is
read as the library's. One occurrence does not show which.

**Resolved by W233 (2026-11-15) — yes: the row read its run on a clock started with the run.** The row declares
`expectBackstop` and `backstopMs: 400`, and `examples/run-flow.ts` started that clock at `start()`: 400 ms had to cover
a worker thread starting, the scheduler's clone refusing the value and the task's retries, before the park the row
asserts. `examples/l6.ts`'s own comment named the failure — *if it were ever too short the row fails loudly, with the
outcome reading `running`* — and that is the one recorded. The clock now starts at the quiescent point where the run
first reads `awaiting_action` (`backstopFromParked`), under the harness's default cap. **Shown by a probe, off-gate**:
with both backstop rows at 1 ms, L6 is 2935 / 0 failed in node and in deno; with the old clock at 1 ms, node fails 19
— 13 in `suspend / nobody comes`, 5 in this row (this question's five), 1 cross-row. Run by the author and again by
the conformity reader. *Not shown*: the original failure itself, which never reproduced; the probe shows the mechanism
and that the row no longer depends on it.
