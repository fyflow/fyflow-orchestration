**Why it is sound, and why only for a loop.** `spec/run-state.md` section 7 refuses any eviction from `inputs`:
a fold over a truncated log reports `completed` while knowing nothing, so an eviction needs a `FoldInput` kind
that lets the fold SAY it was handed less. [P47](../plans/p47-what-may-repeat-in-a-flow-and-how-a-round-hands-on-to-the-next.md)
decision 1 (b′) lets a reader outside a loop name a body node, as after a map (ADR 0044) - but WHICH body nodes
are read from outside is stated by the document, at the two sites P47 fact 14 names. So once round *i + 1* has
opened, everything the rest of the run can still need of rounds 0..*i* is the carried state and those nodes'
outputs. A `loop.compacted { carried, read, through }` element would carry exactly that. A `map` has no such cut:
its instances run at once, so there is no point at which some are finished and the rest not yet opened.

**What it would cost.** A Host showing a compacted round, and `inputOf` for one (ADR 0128), would need events the
library no longer holds - it moves what a Host must keep. Resume would replay from the compacted element rather
than from the settlements, which is a second replay road beside `RN-R26`'s.
