**What happens without it.** `checkWiring` refines an arc leaving a gate in ONE way: on a route the gate's set
names in `keyResolvedRoutes`, `required` is added along **`settings.key`** (ADR 0068; `wiring.ts`' arrival loop).
The built-in `if` has no `settings.key` — its path is inside `when` — so what leaves it on `then` is what arrived,
unrefined. A task after `then` that REQUIRES the key the condition compared reads **`no`** against a producer that
declares the key without requiring it, on a flow that is correct, because the run cannot take `then` without the
key: [Q391](q391.md)'s shape, for `if`. `switch` does not have the problem — its cases are key-resolved routes over
its own `settings.key` — and W154's L1 asserts both.

**The price, measured at [W154](../work-items/w154-the-built-in-if-and-switch.md)'s declaration step:**

| piece | size |
|---|---|
| an interface member saying *on route R these paths resolved*, for paths that are not `settings.key` (e.g. `routesFor` returning `resolvedPaths: { then: [...] }`) — public, in `GATE_TYPE_KEYS` and `routeSetProblem`, with an ADR amending ADR 0068 rules 1-2; W99's assertion binds the shape message to `GATE_TYPE_KEYS` | one member, ~10 lines |
| `if` derives the paths: a leaf with no `default` on `then` (absent is no match for every operator); every member of an `all`; nothing for `any`, for `else`, or for a leaf declaring `default` — and `if` becomes a derived type | ~15 lines |
| the arrival loop refines per path, and asks `keyPathRefusal` per path for the refusing direction | ~15 lines in `wiring.ts` |
| spec rows, `AGENTS.md` section 20, a wiring suite | one item's worth |
