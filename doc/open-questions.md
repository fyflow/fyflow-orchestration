# Open questions

The register. One row per question, ids monotonic, **never reused and never renumbered**
(`doc/workflow.md` section 3). A work item reserves a block before it starts and fills rows from it.

**Status values:** `open` · `deferred` (real, not now, with a reason) · `resolved` (with what
resolved it - an ADR, a spec section, or a plan record).

**Owner** is the work item or plan that will answer it, or `no owner` - which is honest and common
before the first plan exists.

**A leaning is not a decision.** Several rows below carry one, because starting a refinement pass
from a blank page wastes it. Every leaning states the argument against itself. Nothing here is
settled until an ADR says so.

A branch routed away, lost or suspended has **no key**; a join nothing arrived at carries `{}`, which is live because `live-token` fires over an all-exited region. **The argument the `null` rested on is unchanged and is what the answer satisfies**: which terminal event satisfies a join is decided by fan-out completion order, so forwarding *whichever finished last* makes a run's data order-dependent — and carrying **all** of them keyed by branch is not picking one. **`settleJoin` still takes no payload parameter**, the guard that kept this a question rather than a convention; the driver records arrivals as they happen and reads the whole map at the exit. **The order-dependence did not vanish, it MOVED**: integer-like object keys are re-ordered ascending by the language, so a depth-1 join is deterministic for free, while dotted keys keep insertion order — which for a join is settlement order — so the hazard is **invisible at depth 1 and live at depth 2**, and `collectArrivals` pins the order. **A declared reducer is [Q165](#live)**, refused narrowly because a reducer is a function of what the join collects and cannot be specified before this rule was |
| Q154 | Does a fan-out hand ONE payload object to every branch, so a branch mutating it mutates its siblings' input? | **Yes it did, and it is closed in TWO different ways for the two features** — [W34](work-items/w34-what-a-branch-receives-and-what-a-join-carries.md), [ADR 0037](decisions/0037-what-a-branch-receives-is-a-property-of-the-fan-out-and-what-a-join-carries-is-a-property-of-the-region.md) rules 1-3, `JP-R11`. **The invariant is *no two nodes ever receive the same object*.** A `fanout` branch now gets its **own copy** of the value the fanout node received; a `map` instance gets **its own item**, as its own copy, so its instances no longer receive one value at all. **The asymmetry is the finding**: measured at N = 1000 over a 117 KiB payload, a clone per branch is **2207.94 ms** against **1.50 ms** for the shipped one-shared-clone — a factor of ~1470, and **quadratic**, because a map's arity and its payload grow together — while for a `fanout` the same fix is **linear in a number the DOCUMENT declares**: 9.3 / 14.2 / 23.0 / 44.3 ms at arity 2 / 3 / 5 / 10 over a 230 KiB payload against 4.5-4.8 ms for one clone. **The fix that is catastrophic for the feature that needed it is unnecessary for that feature and affordable for the other.** **The unmeasured half is measured**: on a real `FyflowScheduler`, **inline**, branch B's worker saw A's write in its own input *before it ran* and A's view gained B's write *after A returned*; **threaded (`maxThreads: 2`)**, each saw only its own. **`a.payload === b.payload` was `true` in BOTH** — the sharing is a driver-level fact and only its OBSERVABILITY is a pool option the flow author does not control, which is [Q61](#live)'s asymmetry in the opposite direction and the second instance of that class. That is why the rule is not conditioned on the pool: the driver cannot see it, which is `OR-R2`'s own reason for cloning *including where it is redundant*. **And *its own item* was not enough**: `structuredClone` preserves aliasing WITHIN one clone, so `{items: [x, x]}` survives the edge hop as an array holding one object twice — constructed and measured — which is why the rule says *its own copy* |
